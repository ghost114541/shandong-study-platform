# PLAN — 阶段开发与 AI 辅助任务规范（草案）

**已确定开发法**：Windows 原生开发 + Git + macOS 自动化构建；先 PoC，后端到端迭代；每项任务须有需求编号、真实验收、测试结果和提交记录。

## 1. 阶段与出口标准

| 阶段 | 重点 | 必须交付 | 退出条件 |

| P0 文档审查 | 审计/需批准定义、SRS、概念数据与安全边界 | 版本化基线文档 | **OID-001…003 已于 2026-11-10 批准**；接下来复核 SRS、建立授权来源工作清单、分配其他未决议题 |

| P2 最小端到端闭环 | 录题→保存→检索→导出 | 实际桌面程序与数据迁移 | 不靠模拟 UI；真实 SQLite 与 PDF 文件验收通过 |
| P3 主要功能 | 知识库、卷库、编辑、过滤、阅读器、组卷 | 主要页面与真实服务 | 核心用户任务全部可运行 |

## 3. 标准任务卡模板

```markdown
# DEV-XXX — 任务名称
- 状态：TODO / IN_PROGRESS / BLOCKED / REVIEW / DONE
- 关联要求：FR-... / NFR-... / CNT-...
- 先决条件：需要哪个任务/接口/PoC 完成
- 目标：一句话说明可观察的用户/系统行为
- 涉及模块：限定允许改动的位置；超范围必须说明
- 输入测试数据：样本路径、版权/许可状态、schema 版本
- 验收步骤：可复现的操作与预期结果
- 必须运行：单测、集成测试、打包或实际 UI 测试
- 已知风险：未验证平台、数据迁移、回滚需求
- 结果：PASS / FAIL / NOT RUN + 证据引用
- Git commit：提交哈希；未提交改动另行说明
- 状态交接：更新 PROJECT_STATUS.md
```

## 4. AI 编程执行约束

1. 先阅读当前 `PROJECT_STATUS.md`、关联 SRS 和代码，再动手修改。
2. 不自行新增被需求排除的功能；必须改需求时写变更提案，并要求用户批准。
3. 按受影响模块最小改动，避免无关重构；不得删除已有用户数据来“让测试通过”。
4. 不虚构命令输出、跨平台构建或人工审核证据；无法运行的测试记作 `NOT RUN`。
5. 每项任务给出文件变动、编译/测试命令、真实结果、风险与 Git 状态。
6. 完成必要测试后再提交/合并；提交及远程推送按当前工具权限和用户的 Git 工作流执行。

## 5. 文件与仓库管理建议

```text
project-root/
  src/                  # React/TypeScript
  src-tauri/            # Rust/Tauri
  docs/                 # 本包正式文档
  tests/                # 自动化/回归测试
  samples/              # 少量许可合规的测试样本
  scripts/              # 构建及内容校验工具
  PROJECT_STATUS.md     # 当前交接状态
```

- 不把所有大型 PDF、商业教辅和私人资源库直接提交 Git。
- GitHub 私有仓库是推荐远程协作选择，但不是 Git 使用的强制前提。
- 在版本化配置中保持平台差异隔离；Mac 构建任务要有真正的实机测试补充。

## 6. 变更请求流程

```text
提出变化 → 标识 FR/数据/安全影响 → 判断缺陷/必要修正/新增功能
        → 新增功能默认后移 → 需要用户批准时形成 CR-XXX
        → 更新 SRS/模型/测试 → Git 版本化与审查
```

技术库版本调整若不改变用户行为，可在 PoC 证据充分且接口契约不破坏的情况下更新设计；仍需记录，禁止静默背离决策。
